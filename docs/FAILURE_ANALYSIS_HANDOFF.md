## 2. 五类失败模式（核心产出）

按「**在哪一步开始跑偏**」分类，而不是按「过没过」：

| 类 | 失败模式 | 运行 | 步数 | 首次编辑 | tokens | 费用 | 占比 |
|---|---|---|---:|---:|---|---:|---:|---:|
| **A** | 收敛成功 | dvc-4124 / dvc-4185 / dask-7894 | 11/24/17 | **step 3 / 8 / 4** | 446,753 | ¥0.9387 | 16% |
| **B** | **细粒度定位／决策提交失败，最终只读未收敛** | hydra-1791×2、pydantic-8977×2 | 27/27/29/27 | **从不** | 1,084,441 | **¥2.2431** | **39%** |
| **C** | 改对文件，改不对补丁 | hydra-1006×2 | 29/28 | step 12 / 13 | 672,384 | ¥1.3804 | 24% |
| **D** | 规划阶段卡死 | hydra-1791 `plan_execute` t1 | 12 | — | 60,914 | ¥0.1274 | 2% |
| **E** | 改对文件但破坏现有测试 | hydra-1791 `plan_execute` t2 | 45 | step 4（execute 段） | 478,796 | ¥1.0112 | 18% |

合计 = 2,743,288 tokens / ¥5.7008，与 `results.md` 一致。

### 2.1 A 类的共同特征：**早**

三次成功的首次编辑分别在第 **3 / 8 / 4** 步。剩下的步数几乎全部用于"跑测试确认"，
最后干净 `finish`。

对照失败组：B 类**从不编辑**；C/E 类首次编辑在第 12/13 步（已经烧掉一半预算）。

### 2.2 `agent_completed` 完全预测了结果

```
agent_completed = True :  3 次运行，3 次通过
agent_completed = False:  8 次运行，0 次通过
```

依据：`core/agent.py:199` 在跑满 `max_steps` 时返回 `{"result": "达到最大步数，未完成"}`，
而 `real_run.py:305` 用 `agent_completed = not isinstance(result, dict)` 判定。
在这 11 条账本中，`agent_completed=False` 对应跑满步数且未调用终态工具；但这不是通用
语义：此前 Dask smoke 曾出现 `agent_completed=false` 而 evaluator 通过，自由文本和其他预算
退出也可能影响这个布尔量。后续应以结构化 `exit_reason` 为准。

**这条的含义**：现在要解决的问题是「让 Agent 收敛」，不是「让 Agent 改得更好」。
一个跑不完的 Agent，加任何审查环节都没有可审的对象。

代码结构与补丁类型，因此这里只保留相关性假设。

## 4. B 类的现象：**在扫描，但没有收敛到修改**

### 证据：读文件序列是连续、大段、高重叠的

hydra-1791 `single` t2 对 `defaults_list.py` 的读取：

```
48-167   94-167   380-500  500-600  600-700
653-780  168-300  1050-1180  850-1049  760-849
```

pydantic-8977 `single` t2 对 `_generate_schema.py` 的读取：

```
1180-1300  1290-1420  1380-1520  1520-1660
1700-1900  1780-1950  2050-2250  1950-2050
2100-2260  2260-2420
```

**两次都是：在同一个文件里，用 200 行的窗口，一格一格往后挪，覆盖上千行。**

这不是"查阅资料"，这是**逐页翻书找一句话**。

### 因果链

```
① search_code 返回「文件 + chunk 行号范围」（chunk 最大 120 行）
        ↓
② 模型知道"相关内容在这个文件里"，但不知道具体哪一行
        ↓
③ replace_text 要求 old 必须「精确唯一匹配」
        ↓
④ 模型必须亲眼看到那段精确文本才能构造 old
        ↓
⑤ → 开始一页一页读，试图找到那段文本
```

### 根因假设：三者的粒度错位

| 接口 | 粒度 |
|---|---|
| `search_code` | chunk 级（文件、symbol、起止行和最多 120 行内容） |
| `read_file` | 200 行一段 |
| `replace_text` 要求 | 精确到字符的唯一片段 |

**"从文件到行"这一段定位，目前完全靠模型用 200 行窗口自己挪。**

### 一个现成但没被用上的资源

`core/search.py` 的 `_python_chunks` 会为顶层函数或类生成裸 `symbol`，`SearchHit.as_dict()`
也会输出它；但它只遍历 `tree.body`，不支持 qualified 方法名、嵌套定义或 overload。
因此 `read_symbol` 需要递归 AST 索引，不能只给现有 `read_file` 加一个字符串参数。

### 5.1 我上一轮说错了：被拦次数不是 2 次

我先前的说法是"失败的运行里有 6-8 步是在重试被拒的搜索"。**查证后这是错的。**

结合运行历史与各版本 trace 行为，正确记录是：

| 运行 | 检索调用 | 实际执行 | 被预算拦下 |
|---|---:|---:|---:|
| hydra-1791 single t1 | 14 | 14 | **0** |
| pydantic-8977 single t1 | 16 | 16 | **0** |
| hydra-1791 single t2 | 9 | 8 | **1** |
| pydantic-8977 single t2 | 10 | 8 | **2** |

| …（其余同） | | | 0 |
| **hydra-1791 plan_execute t2** | 10 | 8 | **2** |

**整个账本 96 次检索调用里，实际至少 5 次被预算拦下。** single t2 的 3 次拒绝
没有出现在当时的 `result_preview`；plan_execute t2 的 2 次可见。

### 5.2 运行版本映射（已由 Codex 的执行历史确认）

| 账本行 | 实际运行 commit | 结果进入仓库的 commit | 预算/trace 状态 |
|---|---|---|---|
| 最初 6 条 single t1 | `bc54a5d` | `cd142b5` | 尚无搜索预算 |
| 3 条 single t2 | `cd142b5` | `1af95bd` | 预算生效，但搜索拒绝 preview 未保存 |
| plan_execute t1 | `bb0e944` | `acd3463` | 拒绝结果可见 |
| plan_execute t2 | `acd3463` | `ef90451` | 拒绝结果可见，含 planner 终止提醒 |

Claude 的初版判断有误：首批结果是在 `bc54a5d` 上运行，随后与预算实现一起提交进
`cd142b5`；不能把“首次包含结果的 commit”误当成运行代码。旧行本身没有版本字段，
因此该映射仍应标记 `protocol_inferred=true`，其依据是 Codex 的执行历史与 Git 时间线。

**无论哪种，行动结论相同：账本没有记录每一行是在哪一版代码/协议下产生的。**
见 5.4 与 9.2。

### 5.3 `probe.txt` 这条记录的解读

hydra-1006 `single` t2 第 7 步：

```json
{"step": 7, "action": "write_file", "path": "/tmp/probe.txt", "result_chars": 31,
 "result_preview": "拒绝写入：路径 D:\\tmp\\probe.txt 在工作区之外"}
```

**被拒的原因是"路径在工作区之外"，不是扩展名 allowlist。** 这条记录本身是好消息——
`check_inside` 生效了，且结果被记进了 trace。

### 5.4 我关于"trace 盲区"的说法需要收窄

`core/agent.py:158-162` 确认：**trace 记录发生在 `execute_tool` 调用之前**，
所以记录的是**调用**而非**结果**。

但 `agent.py:176-179` 又对**部分**工具补了 `result_preview`：

| 工具 | 结果是否被记录 |
|---|---|
| `write_file` / `replace_text` / `run_command` | ✅ 记录（前 300 字符） |
| `search_code` | ⚠️ **仅当被预算拦下时**记录 |
| `read_file` | ❌ 只记 `result_chars`，不记结果状态 |

所以准确的说法是：**结果信息部分存在，但没有被结构化，无法可靠区分"执行成功"与"被拒"。**
`compact_trace`（`real_run.py:113-130`）只是原样搬运，没有推导状态。

## 6. 建议的优先级

| 优先级 | 做什么 | 打中的失败类 | 占预算 | 实现成本 | 付费 |
|---|---|---:|---:|---|---|
| **P0** | trace 增加显式 `status`（executed / blocked / rejected / error） | 诊断基础设施 | — | 低 | ¥0 |
| **P0** | 把第 2 节的失败分类表写进报告/README | 项目叙事 | — | 低 | ¥0 |
| **P1** | 新增递归 AST 驱动的 `read_symbol` | **B 类** | **39%** | 中 | ¥0 |
| **P1** | 无进展检测：连续 N 步无编辑 → 注入强制转向提示 | B 类（止血） | 39% | 低 | ¥0 |
| **P2** | 探索检索命中窗口标注 | B 类 | 39% | 未知 | ¥0 |
| **P2** | Reviewer + Reviser | C + E 类 | 42% | 高 | 需预算 |

### 为什么 P1 排在 Reviewer 前面

1. **B 类（39%）与 C+E（42%）占比相当**，但 B 类的成因更明确、修法更便宜。
2. **B 类的根因（定位粒度）修好后，C 类和 E 类也会受益**——"改错"很多时候是"看错了地方"的延续。
3. **Reviewer 对 B 类完全无效**：没有补丁可审。

### P1 的具体做法

**① `read_symbol(path, symbol, occurrence, context_lines)`**

使用独立递归 AST 索引生成 qualified name；重名或 overload 时返回候选而不是猜测。
**这是把"200 行窗口挪格子"换成"直接跳到那个函数"。**

**② 检索命中窗口暂缓**

语义检索没有天然的“精确命中行”，离线格式对照也不能证明行为改善。本项先降为 P2，
把时间留给证据更强的 `read_symbol` 和无进展干预。

**③ 无进展检测**

`final_step_prompt` 已经被证明有效——`hydra-1791 plan_execute` t1→t2 的 Planner
就是靠它从"读 10 步不交计划"变成"正常提交"（见 `acd3463`）。
**把同一手法推广到"连续 N 步只读不写"这个条件上**：

```
检测到 9 个完整 LLM turn 没有成功 production mutation →
要求结构化四选一：最小修改 / 一次定向读取 / 结构化放弃 / 明确结束。
```

阈值 9 来自成功样本首次编辑 step 3/8/4，避免在 DVC-4185 原本准备编辑前介入。
按 LLM turn 而不是工具调用计数，被拒编辑不重置，并且只在 single 的首次成功修改前触发一次。

- **不要**继续在 hydra-1791 / pydantic-8977 上盲目加 trial。
  hydra-1791 四次运行吃掉 **38.5% 预算**（¥2.1931）、贡献 0 通过、其中 2 次零改动；

- **不要**把 11 行混在一起报"成功率"。这 11 行至少来自三种协议
  （single t1 / single t2 / plan_execute），且可能来自不同代码版本（见 5.2）。
- **不要**说"多 Agent 更强"、"RAG 提升成功率"——沿用既有口径。
- **不要**把本文第 3 节的规模分界当成已证实的结论；它是**假设**，n=6。
- **不要**说"检索质量没问题"。`real/README.md` 已记录：默认离线检索器 top-10
  只命中 **1/6** 的 gold 文件——这是默认离线后端（hashing + lexical rerank）的成绩，
  不是 BGE 的成绩，两者都不能省掉这个限定。

## 9. 建议的记录改进（低成本、高回报）

### 9.1 trace 增加状态字段

在 `core/agent.py` 记录 trace 时，把 `execute_tool` 的返回结果归类成一个显式字段：

```python
trace_record["status"] = "blocked" | "rejected" | "error" | "ok"
```

判据可以从返回文本推导（"代码检索预算已耗尽" / "拒绝" / "失败"），
也可以让 executor 返回结构化的 `(text, status)`。

**收益**：现在无法可靠回答"这个工具调用了多少次、其中多少次被执行"。
`search_calls`（`real_run.py:342`）现在数的是**调用次数**，会高估真实检索量。

### 9.2 记录协议/代码版本

每一行加上产生它的代码版本（commit sha 或一个手写的 `protocol` 字段）。

**理由**：5.2 那个对不上，正是因为账本无法回答"这一行是在哪一版代码下产生的"。
`§8 不变量`里写的"不同 prompt、工具、策略的结果必须带 strategy/protocol 标识"，
目前只做到了 `strategy`，**缺 protocol/版本**。

### 9.3 报告按失败类聚合

现在的 `generate_report`（`real_run.py:149-175`）按 case 列出。
建议增加一个按**失败类**（A/B/C/D/E）聚合的视图——它比通过率更能指导下一步。

## 10. 对原计划的再评估

`CLAUDE_CODE_HANDOFF.md` §5.4 把失败层级列为 6 层，并判断"项目已经走到第 6 层"。
**从这 11 条 trace 看，这个判断偏高：**

- 第 1 层（能否找到文件）：3 个小仓库过了；3 个大仓库的检索未命中，
  但 **Agent 自己的多轮搜索补回来了**（`gold_file_recall` 在 6/11 行是 100%）。
- 第 3 层（**能否从调查切换到编辑**）：**对 B 类 4 次运行根本没通过**——它们 0 次编辑。
- 第 6 层（发现回归后能否 revision）：**只有 E 类 1 次运行到达过**。

所以"下一步是 Reviewer/Revision"这个结论，**建立在单次观察（hydra-1791 t2）之上**。
它描述的是**最深层**的失败，但不是**最高频**的失败。

**建议**：把 Reviewer 保留为 P2，先做 P0/P1。理由见第 6 节。
